# gogamen-lab-retro (GOG-60 emulation spike)

Defines `LibretroCorePort`, the boundary mirroring the libretro contract
(framebuffer, RAM view, `serialize_state`/`unserialize_state`, run one frame
with an input mask, reset), and validates it with `FreePlayCore`, an original
deterministic in-process core. `Session` adds wrapper state (frame counter,
input history) and a checksummed snapshot format.

## Technical decision
- **Dependency**: none for the spike (std only). Stable-Retro and Libretro are
  deferred; nothing is vendored or fetched.
- **License**: all code original (MIT, workspace license). No ROM, BIOS or
  third-party asset is in the repo; the game is generated by code.
- **Platform**: Linux x86_64 tested. Pure Rust, no unsafe, no FFI.
- **Alternatives and when to choose**:
  - *Libretro C-ABI via `libloading`*: choose for in-process, high-throughput
    use from Rust (no IPC), many cores, exact `retro_serialize` states. Costs:
    `unsafe` FFI, per-core dlopen, core licences (GPL cores) and the user
    supplying ROMs. Implement it as another `LibretroCorePort` impl.
  - *Stable-Retro (Python)*: choose for RL research ecosystems and its
    prebuilt game integrations (reward/done data). Costs: a Python process
    plus IPC, ~1 process per env, harder determinism/packaging.
- **Process limits**: embedded core = 0 extra processes (same thread). A real
  libretro core via dlopen is also in-process (0 extra processes, but one
  loaded shared library and global core state, so typically one instance per
  process: parallel envs need worker processes). Stable-Retro implies one
  Python process per worker.
- **Measurements**: `cargo run --release -p gogamen-lab-retro --example bench`.

## GOG-61 digital adapter (`adapter.rs`)
`Adapter<C: LibretroCorePort>` is a resident, in-process, headless environment
(no IPC, window or audio) implementing `gogamen-core`'s `LiveEnvironment`
(`observe`/`apply`/`reset`) and `BranchableSnapshot` (`snapshot`/`fork`/`restore`).
- **Versioned spec**: `AdapterSpec` = adapter version + access mode +
  `AdapterConfig { frame_skip, reward_fn_version, terminal_fn_version,
  goal_score, max_steps }` + core geometry + action-table version. Its FNV hash
  is stored in snapshots; restoring under a different spec fails with
  `AdapterError::SpecMismatch`. Only reward/terminal v1 exist (score delta;
  goal/horizon); unknown versions are rejected at construction.
- **Errors**: all failures are typed (`AdapterError`). `restore_bytes`
  validates envelope and spec before touching the core, and if the core fails
  it re-applies the previous state (`RollbackFailed` only if that also fails).
- **Declared access = `AccessMode::SnapshotForkable`**. `gogamen-core` has no
  explicit access-mode type (capability is structural: planners only see a
  `GenerativeModel` through `PlanningContext`), so `AccessMode` is a small
  adapter-local declaration. FMC reaches the emulator only via
  `Adapter::planning_model()` (`SnapshotForkModel`), which forks and restores
  per simulated step; the live adapter is never mutated by planning. Use
  `planning_features`/`planning_reward` with `FmcPlanner::plan_with_trace`.
- Tests: `cargo test -p gogamen-lab-retro --test adapter`.

## GOG-111 framebuffer and overlay (studio)
`gogamen-studio` (`retro_session.rs`, `retro_view.rs`) turns the adapter's real
framebuffer (palette indices, bytes passed through unmodified) into a
`gogamen_projection::Texture` and projects overlays in image coordinates. No
sprite is recreated and no commercial ROM is used: the frames come from the
procedural `FreePlayCore` homebrew-style source.
- **License/attribution kept in the view**: `FreePlay homebrew-style core (gogamen-lab-retro): original code, MIT license, no ROM, no third-party assets; frames generated procedurally`
  (`HOMEBREW_LICENSE`); it is shown in the SVG and asserted by a test.
- **Pixel/screen mapping**: integer scale + integer letterbox (`ImageViewport`);
  if the window is smaller than the image it falls back to a centered fractional
  scale (not pixel-exact).
- **Perception**: overlay items are tagged `PerceptionSource::{Privileged,PixelOnly}`
  (`[RAM]` dashed green vs `[PX]` solid orange). The pixel-only view shows only
  detector output and never synthesizes detections or leaks RAM data.
- **Frames vs commands**: dropped frames (slow/disconnected viewer) and emulator
  commands (pause/resume/step/input) have separate counters and records; the
  headless run needs no UI dependency.
- Demo: `cargo run -p gogamen-studio --example retro_svg -- [privileged|pixel] [detect]`.
